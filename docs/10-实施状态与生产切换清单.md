# 实施状态与生产切换清单

## 1. 文档口径

本文基于当前文件所在 Git revision 的代码、测试、构建结果及 `docs/00-09` 汇总实施状态。最后复核日期为 2026-09-03。

状态定义：

- **代码已落地**：对应代码、测试、配置或文档已经进入当前 Git 历史；不等同于已在目标生产环境验证。
- **基础能力已落地**：存在可组合的组件或原语，但业务调用链尚未全部接入。
- **待完成/待验证**：当前历史和文档不能证明已经完成，生产切换时不得按已完成处理。
- 本文不记录真实用户名、密码、token、密钥、生产地址或其他凭据。

## 3. 未完成或尚未接入生产的项目

以下项目必须保持为开放项，直到代码接线、自动化测试、目标环境演练和变更记录均提供证据：

### 3.1 应用与架构

- **Application services 全迁移未完成**：尚未看到 `culvert.application.*` 垂直切片覆盖 Forward、Caddy、Docker、SmolVM、Admin/User 的完整证据；现有大型 Handler 和领域模块仍不能视为全部通过 application service 编排。
- **Web/查询层解耦未完成**：尚不能确认所有 Handler 均已停止直接访问资源 atom、调用领域 mutation 或执行外部 CLI，也不能确认稳定 DTO 和一致快照已覆盖全部页面与 WebSocket 路径。
- **真实 adapter 收口未完成**：进程执行已有公共 adapter，但 Docker/Podman、Caddy、SmolVM、socat、ttyd、iptables、S3/FUSE 的完整业务副作用尚未全部形成可替换、可注入、可独立测试的 adapter。
- **领域事件与可观测性未完成**：request ID、结构化事件、脱敏和审计 sink 原语已落地，但 mutation 审计、持久化审计、指标和告警尚未覆盖所有高风险操作。

### 3.2 持久化、事务与恢复

- **SQLite 尚未成为默认持久化路径**：当前生产路径仍使用 JSON；`culvert.persistence.*` 不由现有 system/runtime 自动启动。
- **JSON -> SQLite 生产迁移尚未执行**：已有只读导入器不等于完成生产数据 dry-run、正式导入、数量/所有者/唯一键校验、完整性检查和恢复演练。
- **业务事务接线部分完成**：用户、Forward 和 Caddy 已具备串行持久化与失败补偿；Docker、SmolVM、S3 mutation 尚未达到同等条件，因此首次切换必须保持对应功能开关关闭。
- **真实 adapter reconciliation 未完成**：当前 reconciliation 是对 desired/actual 快照生成确定性报告；尚未接入 Docker/Podman、SmolVM、Caddy、socat/ttyd、iptables、S3/FUSE、监听端口等真实状态采集，也未形成经审核的自动修复策略。
- **SQLite 默认切换后的备份、恢复和回滚未验证**：现有 JSON 停机备份 runbook 与 SQLite `backup!` 基础能力不能替代目标生产数据的实际恢复演练。

### 3.3 安全与外部服务

- **ttyd 认证代理未完成**：ttyd 已使用 loopback 监听，但当前代码仍使用 ttyd 基本认证参数；尚未看到由主应用或 Caddy 提供的短期、单用途、绑定用户与资源的认证代理及完整过期/撤销测试。
- **真实凭据轮换未验证**：仓库文档要求轮换历史中暴露过的管理员、shell 和外部服务凭据，但 Git 历史不能证明生产侧已经执行。
- **外部命令最小权限未验证**：systemd 模板和 runbook 已存在，但 Docker socket、iptables、挂载、Caddy 等权限必须在目标主机逐项审批和验证；不得通过让整个 JVM 以 root 运行来绕过。
- **真实外部依赖集成测试未完成或无证据**：已在 Linux 用户目录以固定 Temurin 完成禁用高风险 adapter 的基础 smoke；不能据此宣称 Docker/Podman、Caddy reload、SmolVM、socat、ttyd、iptables、S3/FUSE 已完成无残留验证。

### 3.4 生产切换状态

- **JVM 尚不能据此认定为生产默认**：仓库具备内置 Temurin runtime 的 Linux x86_64 jpackage 制品与 systemd 部署骨架，但没有目标生产部署、灰度、观察窗口及回滚演练完成的证据。
- **Temurin 版本必须核验**：构建脚本和 CI 固定 Eclipse Temurin `26.0.2+10`，目标主机无需安装系统 Java；安装时仍必须核验归档摘要及包内 runtime 的供应商、完整版本和 build number。Temurin 26 非 LTS，禁止替换为系统 Java 或自动漂移。
- **Babashka 回退路径仍需保留**：在 JVM 生产观察窗口和数据格式兼容性得到确认前，不应删除 BB 启动能力；同时严禁 BB 与 JVM 写同一数据目录。

## 4. 当前差距概要

代码侧已满足本次 **JVM + JSON、Docker/SmolVM/S3/ttyd 默认关闭** 的候选发布条件；剩余工作主要是生产运维签署，而不是继续扩大重构范围。当前不能正式替换的硬阻塞有 4 类：

1. 目标主机尚未由有权限的运维人员安装 jpackage app-image、systemd unit、专用 `culvert` 账户和受限目录。
2. 尚未对原生产 JSON 与真实 Forward/Caddy/外部资源完成停写清点、备份和回滚点确认。
3. 尚未在正式 systemd cgroup 下完成真实 Forward/Caddy、SIGTERM、异常退出和权限 smoke test。
4. 尚未执行生产观察窗口与变更负责人签署。

2026-09-03 已在内部验证主机的用户隔离目录完成：Temurin `26.0.2+10`、jar SHA-256、JVM readiness/liveness、同数据目录第二实例拒绝、SIGTERM 退出、JSON 备份恢复与日志敏感关键字抽查。本批 jpackage 制品还须在同一 Linux 环境验证包内 runtime、归档摘要及不依赖系统 Java 的启动。该主机无可用免密 sudo，且验证目录不是生产目录，因此这些结果不能替代上述 4 类正式签署。

## 5. 运维必须执行项

以下动作不能由代码提交替代，必须由有授权的运维人员在变更单中记录执行人、时间、环境、制品摘要、结果和回滚点：

1. 从受信 CI 获取不可变 Linux x86_64 jpackage 归档与 SHA-256 文件，在安装前后校验摘要，并记录 Git revision 与 CI run。
2. 验证 app-image 内置 runtime 精确为 Eclipse Temurin `26.0.2+10`；不得替换为系统 Java。
3. 使用非 root 专用账户运行控制面；逐项审批外部命令、socket、网络和挂载权限。
4. 将配置、状态、诊断和备份目录移出源码工作树，校验所有者与权限；配置和备份按敏感数据保护。
5. 轮换历史中可能出现过的管理员、shell、S3、ttyd 或其他外部服务凭据；不得把轮换值写入 Git、日志或变更单正文。
6. 在停写条件下创建一致备份，校验摘要，并在隔离位置执行实际恢复演练。
7. 清点切换前真实资源：用户、Forward、Caddy 规则、容器、VM、端口、iptables、socat/ttyd 进程和挂载。
8. 在受控 Linux 预生产环境完成 HTTP、WebSocket、状态恢复、外部 adapter、SIGTERM、异常退出、磁盘不可写及失败补偿测试。
9. 明确维护窗口、写冻结方法、观察窗口、回滚阈值、上一制品和对应数据备份。
10. 切换时先停止旧实例并人工确认无 BB/第二 JVM 进程写目标目录；单实例锁是纵深保护，不替代人工核对。
11. 切换后检查 liveness、readiness、登录、授权、关键读取和一项可回收写操作，并观察内存、线程、子进程、错误和数据一致性。
12. 若启用 SQLite，另行执行停写、JSON 备份、dry-run、空库导入、计数与唯一键校验、`integrity-check`、启动验证和回滚演练；禁止长期双写 JSON/SQLite。
13. 在真实 reconciliation 尚未接入前，人工核对期望状态和实际外部资源；不得自动删除来源不明的资源。
14. 确认日志、journal、heap dump、崩溃文件和备份不公开且不包含未经控制的凭据输出。

详细命令和目录基线见 `docs/07-JVM部署与运维.md`；SQLite 边界见 `docs/08-SQLite基础与JSON导入.md`。

- [ ] 已按数据格式兼容性选择“仅回退 jar”或“恢复切换前备份”。
- [ ] 上一制品启动后 liveness、readiness 和关键业务 smoke test 已通过。
- [ ] 已人工核对孤儿进程、容器、VM、端口、Caddy、iptables 和挂载。
- [ ] 已记录失败原因、影响范围和再次切换前的整改项。

## 7. 工具链结论

当前项目应继续使用 **`deps.edn + tools.build`，不引入 Leiningen**。

理由如下：

1. 当前依赖、测试、开发 REPL 和构建 alias 已在 `deps.edn` 中明确配置，uberjar、构建元数据、JDK 门禁和 SHA-256 已由 `build.clj` 实现。
2. 现有 CI、部署文档和本地命令已经围绕 Clojure CLI 与 `tools.build` 建立；引入 Leiningen会形成第二套依赖解析和构建入口，增加漂移与维护成本。
3. 当前项目没有必须依赖 Lein 插件生态才能实现的能力。
4. `deps.edn + tools.build` 更贴近当前代码结构，也与 `docs/00`、`docs/02`、`docs/03` 已记录的技术决策一致。

因此，在没有新的、可验证且无法由现有工具链满足的约束前，**`deps.edn + tools.build` 明确优于引入 Leiningen**。JVM 迁移不要求使用 Leiningen，生产切换也不得以改换构建工具作为前置条件。

## 8. 当前结论

当前版本已具备受限范围的 JVM + JSON 候选发布条件，但尚未完成生产替换。首次切换必须保持 `dockerMutationsEnabled=false`、`smolvmMutationsEnabled=false`、`ttydEnabled=false` 和 `s3.enabled=false`；若生产存在 Docker、SmolVM 或 S3 受管记录，必须停止切换并先完成专项迁移。

生产切换必须以第 6 节逐项执行和留证为准；在目标 systemd 部署、生产数据备份恢复、真实资源核对、观察窗口和回滚准备完成前，保持现有生产入口与数据路径，不进行无证据切换。
