# 阶段 5：持久化与并发治理

## 1. 阶段目标

消除端口、配额、内存状态、磁盘状态和外部资源之间的主要竞争与不一致风险，使资源操作可恢复、可审计、可重试。

## 2. 核心问题

当前典型操作跨越：

1. 配额检查；
2. 端口选择；
3. Docker/SmolVM/socat/iptables/ttyd 调用；
4. Caddy 修改；
5. atom 更新；
6. JSON 写入。

这些步骤不是一个事务。原子文件替换只能防止半文件，不能防止并发丢失更新，也不能回滚外部副作用。

## 3. 工作项

### 3.1 定义资源状态机

为容器、VM、转发、代理绑定定义明确状态：

```text
requested
provisioning
running
stopping
deleting
error
deleted
```

每次转换定义：

- 前置状态；
- 授权规则；
- 外部步骤；
- 成功状态；
- 失败状态；
- 可重试性；
- 补偿动作。

验收：

- 非法状态转换被拒绝；
- 中途失败不会被记录为成功；
- `error` 状态包含可操作的失败原因。

### 3.2 原子化端口与配额预留

设计统一资源预留服务：

```clojure
(reserve! repository actor request)
(commit! repository reservation-id resource-id)
(release! repository reservation-id)
```

预留内容可以包括：

- 用户资源数量；
- CPU/内存预算；
- ttyd 端口；
- host 转发端口；
- 域名或 worker 唯一键。

要求：

- 检查和预留在同一事务内；
- 预留有 TTL，崩溃后可以回收；
- 创建失败必须释放；
- 数据库提供唯一约束作为最终保护；
- Docker 与 SmolVM 是否共享 CPU/内存预算必须形成明确业务规则。

### 3.3 评估并迁移到 SQLite

推荐使用 SQLite 作为单机部署的默认状态存储，原因：

- 与当前单机控制面匹配；
- 支持事务和唯一约束；
- 运维成本低；
- 备份和恢复简单；
- JVM 下 JDBC/next.jdbc 支持成熟。

候选表：

```text
users
sessions
resources
port_bindings
proxy_rules
reservations
resource_events
schema_migrations
```

任务：

1. 设计 schema 和索引；
2. 增加 schema version；
3. 建立 repository protocol；
4. 先实现 SQLite repository，再保留 JSON 只读导入器；
5. 编写 JSON -> SQLite 一次性迁移工具；
6. 迁移前后进行数量和关键字段校验；
7. 建立备份、恢复和完整性检查命令。

不要让应用长期双写 JSON 和 SQLite，否则会引入新的不一致源。迁移期可采用：停写、备份、导入、校验、切换。

### 3.4 实现 saga 和补偿

每个外部操作步骤返回结果及补偿信息：

```clojure
{:value result
 :compensate #(undo result)}
```

失败时逆序补偿，例如创建容器：

1. 预留配额和端口；
2. 创建 runtime；
3. 启动 ttyd；
4. 添加 Caddy；
5. 提交资源状态。

任一步骤失败，逆序清理已完成步骤。

要求：

- 补偿必须幂等；
- 清理失败不能被空 catch 吞掉；
- saga 结果写入资源事件；
- 无法自动补偿时进入 `error` 并产生管理员告警。

### 3.5 启动 reconciliation

启动时对比期望状态和实际状态：

- 数据库资源记录；
- Docker/Podman 容器；
- SmolVM；
- Caddy 配置；
- socat/ttyd 进程；
- iptables 规则；
- S3/FUSE 挂载；
- 实际监听端口。

处理策略：

- 自动修复明确安全且幂等的问题；
- 高风险差异只报告，不自动删除未知资源；
- 孤儿资源记录为告警并提供清理命令；
- reconciliation 每一步可重复执行。

### 3.6 外部命令可靠性

统一要求：

- argv 调用，不拼接 shell 字符串；
- 明确超时；
- 捕获 stdout/stderr/exit code/duration；
- 非零退出默认失败；
- 对可接受退出码显式白名单；
- 支持取消和进程树清理；
- 日志脱敏；
- retry 只用于明确幂等且短暂性错误。

## 4. 数据迁移计划

### 4.1 预演

1. 复制脱敏生产数据；
2. 运行 schema 校验；
3. 导入 SQLite；
4. 对比用户、资源、端口和代理数量；
5. 启动只读验证；
6. 执行完整备份和恢复。

### 4.2 正式迁移

1. 停止写请求；
2. 停止服务；
3. 备份 JSON 和外部资源清单；
4. 导入 SQLite；
5. 校验数量、所有者、唯一键和配额；
6. 使用 SQLite 启动；
7. 运行 reconciliation；
8. 开放写请求。

### 4.3 回滚

- 迁移后不立即删除 JSON 备份；
- 回滚时停止新实例，恢复迁移前数据库和对应版本；
- 禁止将迁移后 SQLite 状态未经转换直接回写旧 JSON；
- 若迁移期间发生业务写入，必须使用逆向迁移工具或接受维护窗口内回滚到旧时间点。

## 5. 测试要求

- 同端口并发预留只有一个成功；
- 配额边界并发创建不会超限；
- reservation TTL 回收；
- 每个 saga 步骤失败时的补偿；
- 补偿自身失败；
- SQLite 事务回滚；
- JSON 损坏和迁移失败；
- reconciliation 幂等；
- 服务崩溃后重启恢复。

## 6. 退出标准

- 端口和配额由事务性 repository 管理；
- 多个请求不会通过 TOCTOU 突破约束；
- 资源操作具备明确状态机和补偿；
- 数据损坏不会被静默当成空数据库；
- 启动 reconciliation 可以报告并处理状态漂移；
- 备份与恢复经过实际演练。
